The fastest way to run Sunred yourself is Docker Compose. Sunred publishes images to GitHub Container Registry on every push to `main` and every release:

| Image | Registry                        |
| ----- | ------------------------------- |
| API   | `ghcr.io/fuegoio/sunred-api` |
| Web   | `ghcr.io/fuegoio/sunred-web` |
| Relay | `ghcr.io/fuegoio/sunred-relay` |

Tags: `latest` (main branch), `1.2.3` / `v1.2.3` (release), `1.2` (minor), `1` (major), `sha-<short>` (commit).

Both containers run as a non-root user (`uid 10001`). The API listens on port 8080, the web app on port 3000.

## Run the stack

The compose file below brings up the API, the web app, and the relay, each with its own PostgreSQL database. Replace the password and domain placeholders before you start.

```yaml
services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: sunred
      POSTGRES_PASSWORD: <db-password>
      POSTGRES_DB: sunred
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U sunred"]
      interval: 5s
      timeout: 3s
      retries: 10

  api:
    image: ghcr.io/fuegoio/sunred-api:latest
    ports:
      - "8080:8080"
    environment:
      SUNRED_DATABASE_URL: postgres://sunred:<db-password>@postgres:5432/sunred?sslmode=disable
      SUNRED_BASE_URL: https://api.your-domain.com
      SUNRED_WEB_URL: https://your-domain.com
      SUNRED_RELAY_URL: http://relay:9090
      SUNRED_OAUTH_REDIRECT_URL: https://api.your-domain.com/auth/oauth/callback
    depends_on:
      postgres:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost:8080/v1/health"]
      interval: 30s
      timeout: 5s
      retries: 3

  web:
    image: ghcr.io/fuegoio/sunred-web:latest
    ports:
      - "3000:3000"
    environment:
      SUNRED_API_URL: http://api:8080
      NEXT_PUBLIC_SUNRED_API_URL: https://api.your-domain.com
    depends_on:
      api:
        condition: service_healthy

  relay-postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: sunred
      POSTGRES_PASSWORD: <relay-db-password>
      POSTGRES_DB: sunred_relay
    volumes:
      - relay-pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U sunred"]
      interval: 5s
      timeout: 3s
      retries: 10

  relay:
    image: ghcr.io/fuegoio/sunred-relay:latest
    ports:
      - "9090:9090"
    environment:
      RELAY_DATABASE_URL: postgres://sunred:<relay-db-password>@relay-postgres:5432/sunred_relay?sslmode=disable
      RELAY_HTTP_ADDR: ":9090"
    depends_on:
      relay-postgres:
        condition: service_healthy

volumes:
  pgdata:
  relay-pgdata:
```

Bring the stack up:

```bash
docker compose up -d
```

Migrations don't run on their own — run them once on first start. The API and relay each have their own database:

```bash
docker compose exec api /app/sunred --migrate
docker compose exec relay /app/sunred-relay --migrate
```

Two variables tell the web app where the API is, and they're not interchangeable. `SUNRED_API_URL` is the server-side URL the web container uses to reach the API over the Docker network. `NEXT_PUBLIC_SUNRED_API_URL` is baked into the browser bundle and must be publicly reachable.

## Run the relay (optional)

The `relay` service is optional but recommended — it enables cross-instance
social features (global counts, federated shares). See
[AT Proto & identity](/self-hosting/at-proto) for what it does and how to
configure it. Users log in with their own AT Proto handle — the default PDS is
`https://snrd.social`, or users can bring their own PDS.
