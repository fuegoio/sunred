title: AT Proto & identity
description: How Sunred uses AT Proto for identity, OAuth login with a PDS, and the relay.

Sunred uses the [AT Protocol](https://atproto.com) for identity. Users log in
with an AT Proto handle — the same account they use on Bluesky or any other
AT Proto client. There are no Sunred-specific passwords.

This page covers what an operator needs to know: the components involved, how
login works, and how to run the PDS and relay alongside Sunred.

## How identity works

Every Sunred user is identified by a **DID** — a persistent identifier stored
on their **PDS** (Personal Data Server). A handle (`alice.bsky.social`,
`bob.sunred.app`) is a human-readable alias that resolves to a DID.

```
handle  ──resolve──▶  DID  ──points to──▶  PDS  ──holds──▶  user records
```

Sunred does not store passwords or issue its own identities. It authenticates
users against their PDS using **AT Proto OAuth** (OAuth 2.0 with PKCE, DPoP,
and PAR). After a successful login, Sunred issues its own session cookie so
the web app can make authenticated requests.

### Any server, any DID

Every Sunred server can authenticate **any** DID, regardless of which PDS
hosts it. A user with a Bluesky account (`alice.bsky.social`) and a user with
an account on your own PDS (`bob.your-domain.com`) can both log into the same
Sunred instance. You are not limited to users on your PDS.

This means Sunred is a **cache and view** of each user's AT Proto data, not
the source of truth. The PDS is the source of truth.

## Components

A full Sunred deployment has four pieces:

| Component | Role | Required? |
| --- | --- | --- |
| API | Sunred REST server, session issuer, PDS/relay client | yes |
| Web | Next.js frontend | yes |
| PDS | Hosts user records, handles OAuth | external — users bring their own |
| Relay | Aggregates `io.sunred.*` records across PDSes | recommended |

### The PDS

Each user's data lives on a PDS — but Sunred does not run or ship a PDS. Users
log in with their own AT Proto handle, typically a Bluesky account
(`*.bsky.social`) or an account on a personal PDS they run themselves. Sunred
authenticates against the user's PDS at login time via OAuth.

If you want to offer accounts on your own domain, you can run a PDS separately
using the [official PDS image](https://github.com/bluesky-social/pds). That's a
deployment decision outside Sunred's scope — Sunred works with any
standards-compliant AT Proto PDS, yours or anyone else's.

### Offering signup

The login page shows a **Continue with [PDS]** button that starts the OAuth
flow against the instance's default PDS. The PDS decides whether to show
login or signup — users without an existing account can create one on that
PDS and are logged into Sunred in one step. The default PDS is configured
on the web side via `NEXT_PUBLIC_SUNRED_DEFAULT_PDS` (default
`https://snrd.social`).

Users who already have an AT Proto account (Bluesky, another PDS) can always
click **Login with a different handle** and enter their handle, regardless of
the default PDS.

### The relay

The relay watches the repo streams of every PDS that hosts an Sunred user and
aggregates `io.sunred.*` records (follows, article shares, stars, feed
subscriptions) into global counts. It then streams those events back to Sunred instances so
they stay in sync across the federated network. The relay also indexes every
known DID and handle, enabling cross-instance user search and follow.

The relay is a separate Go service with its own database. Point the API at it
with `SUNRED_RELAY_URL`. If unset, cross-instance social features (global
follower counts, federated shares, cross-instance user search) are disabled —
the instance still works standalone.

## Data responsibilities

Each component owns a different slice of the data. This matters for backups and
for understanding what federates versus what stays local.

| Data | Source of truth | Instance (API) | Relay |
| --- | --- | --- | --- |
| User identity (DID, handle) | PDS | cached for login | tracked |
| `io.sunred.*` records (follows, shares, stars, subscriptions) | PDS | mirrored cache | aggregated copy |
| Profile (display name, bio) | PDS (`app.bsky.actor.profile`) | cached for display | never |
| Article & feed content (entry bodies, enclosures) | source feeds | fetched and stored | never |
| Per-user private state (read, folders, settings) | the instance | yes | never |

### The instance (API)

The API keeps its own PostgreSQL database with three kinds of data:

- **Feed content** — article bodies, enclosures, and feed metadata. The
  instance's scheduler fetches these from the source feeds on a poll cycle. They
  never come from the PDS or the relay.
- **A derived cache** of each user's `io.sunred.*` records, mirrored from their
  PDS on first login and kept in sync through the relay. The PDS stays canonical;
  the cache can be rebuilt from it.
- **Instance-local state** that never federates — read and starred state,
  folders, per-instance settings. It stays on the instance where it was created
  and does not follow the DID to another instance.

The API also stores the OAuth tokens and DPoP keypair it uses to sign PDS
requests for each account.

### The relay

The relay's own PostgreSQL database holds **only public social-graph metadata**
aggregated across PDSes: who follows whom, which articles were shared (URL and
title, never the body), and who subscribes to which feed. It uses that to
compute global counts and stream events back to instances.

The relay never stores article content, feed entries, per-user private state, or
OAuth material. Losing the relay database disables cross-instance features until
it re-aggregates from PDS repo streams; no user content is lost.

## Login flow

```
1. User clicks "Continue with [PDS]" or enters their handle in the web UI
2. Sunred resolves the identifier (PDS URL resolves directly; a handle
   resolves handle → DID → PDS endpoint)
3. Sunred registers as an OAuth client with that PDS (dynamic registration)
4. Sunred sends a Pushed Authorization Request (PAR) and redirects the
   user to the PDS's authorize endpoint with a PKCE challenge
5. User approves on the PDS
6. PDS redirects back to Sunred's callback with an authorization code
7. Sunred exchanges the code for DPoP-bound access + refresh tokens,
   stored keyed by the user's DID
8. Sunred creates or looks up the local user row by DID, issues a
   session cookie, and redirects to the app
```

In development, the OAuth callback URL uses `127.0.0.1` (RFC 8252 rejects
`localhost`). The API redirects `127.0.0.1` callbacks to `localhost` so the
session cookie (host-only on `localhost`) is shared across the web (port 3000)
and API (port 8080).

Sunred holds a DPoP keypair per account so it can sign PDS requests with the
bound access token. You do not need to manage these keys manually — Sunred
generates and stores them.

## Sync on first login

Because Sunred is a cache of the user's PDS, the first time a DID logs into a
given instance Sunred backfills the local database from the PDS:

1. List the user's `io.sunred.*` records (`com.atproto.repo.listRecords` for
   each collection).
2. Populate the local cache: follows, shared articles, starred entries, and
   feed subscriptions.
3. Announce the user to the relay so it starts subscribing to that PDS repo
   stream.
4. Subscribe to the relay's event stream for that DID to receive live updates.

Subsequent logins reuse the existing cache and resume the relay subscription.
Local-only state that is not part of the AT Proto records — read state,
folders, per-instance settings — stays on the instance where it was created
and does not transfer with the DID.

## Writing back to the PDS

When a user follows someone, shares an article, or subscribes to a feed,
Sunred writes an `io.sunred.*` record to their PDS repo (signed with the
DPoP-bound access token). The relay picks up the record from the PDS repo
stream and federates it. The local cache and the PDS stay in sync — the PDS is
the canonical copy, the cache is derived.

## Records Sunred uses

| Collection | Purpose |
| --- | --- |
| `io.sunred.graph.follow` | A follow relationship between two DIDs |
| `io.sunred.share.article` | A shared article with metadata (URL, title, feed) |
| `io.sunred.entry.star` | A starred/bookmarked article with the same metadata as a share |
| `io.sunred.feed.subscription` | A feed the user subscribes to |

These are public records on the user's PDS. Other Sunred instances and the
relay read them to build the federated social graph.

## Configuration

See [Configuration](/self-hosting/configuration) for the environment variables
that control relay and OAuth behavior. The key ones:

- `SUNRED_RELAY_URL` — the relay endpoint (optional; enables cross-instance
  social features).
- `SUNRED_BASE_URL` — the public URL of the API. The OAuth callback URL
  derives from this (`<BaseURL>/auth/oauth/callback`). Must use `127.0.0.1`
  (not `localhost`) in dev for RFC 8252 compliance.
- `NEXT_PUBLIC_SUNRED_DEFAULT_PDS` — the default PDS shown on the login page
  (web-only config; defaults to `https://snrd.social`).
