## Terminate TLS with a reverse proxy

Neither service terminates TLS directly, so put both behind a reverse proxy —
nginx, Caddy, and Traefik all work. In the example below the API runs on its
own subdomain (`api.your-domain.com`) and the web app serves the main domain.

```nginx
server {
    listen 443 ssl;
    server_name api.your-domain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 443 ssl;
    server_name your-domain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## Share a session across origins

When the API and the web app are served from different origins (e.g.
`api.sunred.app` and `app.sunred.app`), the default session cookie is
host-only on the API domain, so the web app never receives it. How you fix
this depends on whether the two share a registrable domain.

### Same registrable domain (subdomains)

If the API and web app share a registrable domain (e.g. `api.sunred.app` and
`app.sunred.app` both under `sunred.app`), set the cookie `Domain` to that
registrable domain. The browser then sends the session cookie to both the web
app and the API — requests between them are same-site, so the default
`SameSite=Lax` works:

```
SUNRED_COOKIE_SECURE=true
SUNRED_COOKIE_DOMAIN=sunred.app
SUNRED_TRUSTED_ORIGINS=https://app.sunred.app
```

`SUNRED_COOKIE_DOMAIN` must be a bare host (no scheme or path). `Secure`
requires the API to be served over HTTPS.

### Different registrable domains

If the API and web app are on entirely different registrable domains (e.g.
`api.sunred.app` and `myapp.com`), a shared cookie domain isn't possible. Use
`SameSite=None` so the browser sends the cookie cross-site:

```
SUNRED_COOKIE_SECURE=true
SUNRED_COOKIE_SAMESITE=none
SUNRED_TRUSTED_ORIGINS=https://myapp.com
```

Browsers reject `SameSite=None` without `Secure`, so the API rejects that
combination at startup. Set `SUNRED_TRUSTED_ORIGINS` to the web app origin(s)
so the API only returns `Access-Control-Allow-Credentials` for trusted
frontends. `SUNRED_WEB_URL` is always added to the allowlist automatically, so
you only need to list any additional origins.

## Back up the databases

Sunred uses two separate PostgreSQL databases — one for the instance (API) and
one for the relay. See [Data responsibilities](/self-hosting/at-proto#data-responsibilities)
for what each holds.

The instance database is the one that matters: it holds feed content, the
mirrored PDS cache, and instance-local state (read state, folders, settings).
Back it up regularly.

```bash
# Create a backup of the instance database
docker compose exec postgres pg_dump -U sunred sunred > backup.sql

# Restore from a backup
cat backup.sql | docker compose exec -T postgres psql -U sunred sunred
```

The relay database holds only aggregated social-graph metadata and can be
rebuilt by re-subscribing to PDS repo streams, so it doesn't need the same
backup regime. Back it up if you want to avoid the re-aggregation delay:

```bash
docker compose exec relay-postgres pg_dump -U sunred sunred_relay > relay-backup.sql
```

For automated backups, schedule `pg_dump` with a cron job and store the dumps
off-site.
